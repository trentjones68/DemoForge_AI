# DemoForge AI architecture decisions and Phase 1 plan

Review baseline dated 2026-11-18. Sources are the supplied `01_PRD.md` v1.0, `02_ARCHITECTURE.md`, and `03_BUILD_PROMPTS.md`. The checkout had no `docs/` directory at review time. The PRD provides product scope, the architecture provides stack and system constraints, and the build prompts provide sequencing suggestions. This document distinguishes baseline decisions, proposed designs to validate, and open questions. It records design work only.

## Architecture review

The documents describe a coherent discovery-to-export workflow and a viable stack. The API and schema sketches need the following decisions before they can support the PRD's acceptance criteria.

| Finding | Impact and disposition |
| --- | --- |
| RLS is required, but the API's SQLAlchemy connection identity, worker identity, and Storage authorization paths are unspecified. A default owner or service-role connection can bypass policy. | Block the tenant foundation until the API and pooled-connection policy tests pass. Prove worker and Storage isolation before their first customer-data flows. See D2. |
| Persona and role names differ, ownership rules are ambiguous, and onboarding and membership lifecycle are missing from the API sketch. | Approve an operation-level role matrix. Explicitly cover invite/revoke, ownership, admin scope, viewers, visibility, and the first workspace owner. See Q1. |

## Decisions

### D1. Preserve the approved stack and Phase 1 scope

**Baseline.** Use Next.js App Router, TypeScript, Tailwind and shadcn/ui; React Query or server actions where appropriate. Use FastAPI, Python 3.12+, Pydantic v2, SQLAlchemy or SQLModel and Alembic. Use Supabase Postgres, Supabase Auth and private Supabase Storage, a durable managed queue and Python worker, and OpenAI behind a provider adapter. Deploy web on Vercel and API and worker on managed Python hosting. Start with deterministic service orchestration. pgvector and LangGraph remain optional. Phase 1 produces reviewed documents. Automated tenant configuration, executable demo scripts, autonomous actions, real-time recording, speech-to-text, CRM writeback and customer emailing are outside Phase 1.

**Proposed scaffold defaults.** Use SQLAlchemy 2 and versioned JSON Schemas, strict TypeScript, Pydantic validation at external boundaries, and a strict Python checker. Start with a small provider-neutral worker boundary. Redis + RQ is a candidate from the architecture, pending a restart and durability evaluation before M4a. Pin toolchain and library versions in M0 and add later dependencies only when exercised.

### D2. Enforce tenant isolation at every persistence boundary

**Baseline.** Supabase JWT authentication, current workspace membership and role checks in FastAPI, RLS for every tenant-owned table and protected Storage.

**Proposed design to verify in M1.** Validate Supabase JWTs using configured issuer, audience, trusted keys and allowed algorithms. Use the verified subject in a transaction-scoped request context with a dedicated non-owner, non-`BYPASSRLS` role. Set identity only after verification and keep it scoped to each transaction. Prove that RLS observes the intended identity with the selected connection mode and that reused connections clear it after commit and rollback. Reject missing context and check membership against the database. Review policy helper privileges and fixed search paths if privileged helpers are needed. Limit grants, avoid RLS bypass on all tenant-facing request paths, and use tenant-bound uniqueness and composite foreign keys for parent/child, evidence and revision links.

Separate migration, request, background processing and maintenance credentials. Workers load a persisted job by opaque ID, derive context from trusted persisted state, and validate references before running. Keep discovery content out of queue messages. Use private object keys with workspace and resource identifiers. Authorize against the database record before issuing signed download URLs. Prefer caller-scoped Storage access where it enforces object policies. If worker Storage operations need broader credentials, isolate them behind a narrow service boundary and test scope independently. Use authorization-aware cache keys and private or no-store responses for sensitive data. Test direct API IDs, list filters, child relationships, URL issuance, direct Storage requests, revoked or downgraded membership, and worker dispatch with two workspaces.

### D3. Treat ingestion and transcript handling as sensitive

**Baseline.** Accept paste, TXT, Markdown, DOCX and text-based PDF, plus an optional separately attributed Plaud summary. Store originals privately and preserve stable source locators. Scanned PDFs get an actionable error. Recording consent, retention and deletion are required.

**Proposed controls.** Enforce upload and extracted byte limits, page/decompression limits, parser time and resource bounds, content/MIME verification, safe file names and sanitization. Parse in an isolated worker or equivalent constrained process with no outbound network access. Avoid fetching embedded references or rendering untrusted markup as executable content. Quarantine until validation and required scanning complete. Handle interrupted uploads and failed jobs with bounded cleanup. Use per-workspace rate limits and quotas. Persist source hash, workspace, session, type, import method, observed metadata, consent attestation and immutable source revision. Use context-aware content deduplication and preserve deliberate reuse across separate sessions. Protect paste data and derived artifacts at the same level as uploaded files. Use short-lived URLs, document the remaining access window after revocation, and prohibit sensitive content in diagnostics or analytics.

### D4. Evidence, approval and revisions

**Proposed resolution of the PRD and build prompts.**

- Evidence links identify a stable segment in an immutable source revision within the same workspace and discovery session. Store segment order, offsets in the extracted text, timestamp/speaker when available, and a verified quote span where shown. For DOCX/PDF, use page or other source locators when available. Treat a separately attributed summary as summary evidence. Never present it as a verbatim transcript quote.
- Label findings as directly evidenced, inference, unknown or contradictory. Validate evidence scope and references and verify quoted spans against stored text before persisting accepted model output. Evidence presence and span validation establish provenance. Human review determines whether the source supports the claim. Capture extraction run, schema/prompt/model versions and review rationale as appropriate. Product claims require catalog evidence.
- Insights start as drafts. Authorized users approve a specific insight revision. Normalized requirements become separate drafts based on approved insights. Support manually entered requirements with human attribution and explicit approval. Retain source links and gaps. Downstream mapping consumes approved requirement revisions and a pinned product/catalog version. A human reviews mappings and overrides with rationale. Only reviewed mappings feed storyboard proposals. An absence of evidence yields unknown. Partial and unsupported claims require explicit catalog evidence.
- Storyboards pin reviewed mappings and approved requirements. A material edit creates a new revision. Approvals stay attached to their original revisions. The current readiness screen surfaces stale inputs, caveats and unsupported or unknown assumptions. Regenerate one section into a proposal, keep other sections and manual edits intact, and require explicit replacement or conflict resolution when the base revision changed. Atomically enforce that accepted section durations sum to the target.
- Proposed MVP export gate. An authorized user exports an explicitly approved storyboard revision. Preserve caveats, provenance and approval status in both formats, and omit raw transcript excerpts by default. Use scoped, authorized evidence references rather than embedding signed URLs. An export can preserve explicitly reviewed blockers and still be marked not demo-ready. The UI must never indicate demo readiness while mandatory approvals are missing, evidence is stale, or a required scenario lacks support.

### D5. Make worker jobs durable and replay-safe

**Baseline.** Critical work uses a durable queue and worker. Expose queued, running, succeeded and failed states, retry and safe errors.

**Proposed design.** Store job, workspace, kind, input revision, tenant-scoped idempotency key, attempt and version/lease state in Postgres. Persist a dispatch record atomically with the job and reconcile undispatched jobs after outages. Persist results and terminal transitions atomically where possible. Bound retries and timeouts, recover expired leases, prevent stale workers from writing results, and recheck permission for user-initiated retry. Keep provider calls idempotent where supported and budget for repeated calls after interruption. Surface request/job IDs and categorized failures. Use a deterministic fake provider for CI and a separate synthetic staging smoke for the live provider.

### D6. Verify Plaud before enabling automation

**Baseline.** Manual Plaud transcript/summary import is the Phase 1 baseline. Keep webhooks disabled pending verification. Plaud access, a particular event payload, a public API, and transcript delivery on any plan are unverified.

**Prompt 10 outcome.** The supplied PRD, architecture and build prompts describe
the intended application interface. They contain no official provider delivery
contract. The fallback JSON text import uses the same signed-in workspace
authorization and discovery pipeline as manual upload. [Plaud import and verification record](PLAUD.md)

**Gate.** Collect current official Plaud and intermediary documentation, plan and region availability, and sanitized payload samples from the intended account. Confirm event semantics, whether full transcript, summary or files are delivered, authentication or signature support and a secure alternative if unavailable, event identifiers, timestamps, replay, retry and quotas, and customer authorization and data transfer terms. Reproduce delivery and failure/retry in a sandbox, including workspace binding and dedupe by workspace/provider/external ID with content hash as appropriate. Record the supported contract before opening implementation. Use the manual path if delivery or authentication cannot be established. Keep automation off by default and subject to an explicit enablement decision.

### D7. Require security, privacy and operational release evidence

**Baseline plus controls to verify.** Use encryption in transit and at rest, least privilege, dedicated secrets, safe errors and synthetic fixtures only in dev/staging. Treat transcripts, catalog documents, metadata and model outputs as untrusted. Bound model input and output, validate structured results, disable tools and arbitrary external actions, and retain schema versions and budgets. Strip customer content from app logs, traces and retries. Control PDF rendering and never fetch remote assets from untrusted content. Require documented recording consent and a production privacy review covering legal basis, provider processing and retention, residency, deletion, exports and backups. Avoid claims of regulatory compliance based on technical controls alone.
